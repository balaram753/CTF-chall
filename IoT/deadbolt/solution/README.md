# Deadbolt — solution

**Vuln:** hash length extension against a `SHA256(secret ‖ message)` token MAC, reached through a proprietary wire framing, with the flag held only on the live device.

**Fallback flag:** `DNCTF{deadbolt_l3ngth_3xtension_ala_carte}` (real events use one shared static flag per the notes at the end; a genuinely per-team flag needs a container plugin).

---

## 0. Why this resists "paste the handout into an AI"

The flag is not on the flash, not in the binary, and not derivable from either. `strings` on the carved `lockd` shows exactly two `DNCTF{...}`-shaped things and neither is the answer:

- `DNCTF{local_dev_instance_not_the_real_flag}` — the placeholder printed only when the binary runs with no `FLAG` in its environment (i.e. when a player runs it on their own machine).
- `d3adb0lt.dev.key` — the development signing key, used only by that same stand-alone instance.

The scored flag lives only in the live device's `FLAG` environment variable and only comes out after a correct, interactive attack against a per-connection nonce. Hand the file to a model and, at best, it explains the bug and hands back the placeholder. That is the honest bar: you cannot make a static file un-solvable by a capable agent, so the flag was moved off the file and behind a live interaction.

## 2. Stage 2 — reverse the wire protocol

Run it and poke it:

```sh
./usr/bin/lockd &      # prints: lockd listening on 6000
```

`nc`/`telnet` get you nothing readable, because the wire is **framed and masked**, not text. Two layers to recover from the binary.

### 2a. The frame

Every message on the wire is:

```text
0xDB 0x01 | len[2] big-endian | payload      (len = number of payload bytes)
```

### 2b. The payload mask

The payload is XORed with a keystream generated by a tiny LCG. In the binary it's the loop that multiplies the running key by 33 and adds 7:

```text
k = 0x5a
for each payload byte:  byte ^= k ;  k = (k*33 + 7) & 0xff
```

So the keystream begins `5a a1 c8 cf ...` (0x5a → 0x5a*33+7 = 0xa1 → 0xa1*33+7 = 0xc8 → …). XOR is symmetric, so the same routine encodes and decodes. Reimplement it (`solve.py: _mask`) and the wire becomes readable.

### 2c. What the device says

On connect the lock sends a **guest token it signed for you**:

```text
salt=<32-hex-nonce>&uid=1000&role=guest&sig=<64-hex>
```

and the signature is (this is the whole game):

```text
sig = SHA256( secret ‖ "salt=<nonce>&uid=1000&role=guest" )
```

The command handler then accepts **any** message ending in `&sig=<hex>` whose signature recomputes correctly under that same `SHA256(secret ‖ msg)` construction, and honors the `role` and `cmd` fields inside it. The field parser splits on `&`, takes `key=value`, skips junk tokens, and on a repeated key **the last occurrence wins** (see `get_field`). `role=admin` + `cmd=dump` returns the vault.

Interesting strings that map straight onto this:

```text
salt=%s&uid=1000&role=guest
%s&sig=%s
&sig=
role   cmd   dump   unlock
ok=1&vault=%s
err=denied&need=admin   err=badsig   err=unsigned
```

You are never meant to learn `secret`. You don't need to.

## 3. Stage 3 — the vulnerability: hash length extension

`sig = SHA256(secret ‖ msg)` is the textbook broken MAC. SHA-256 is Merkle–Damgård: its output *is* its full internal state after absorbing `secret ‖ msg ‖ padding`. If you know that output, you can set an SHA-256 engine to that state and **keep hashing more data**, producing a valid tag for a longer message, without knowing `secret`.

Concretely, SHA-256 pads a message of length `L` bytes with:

```text
glue = 0x80  ‖  0x00 × k  ‖  uint64_be(L * 8)      (k chosen so L+1+k+8 ≡ 0 mod 64)
```

Given the guest token `(msg, sig)` you have a valid tag for `secret ‖ msg`. Choose an extension:

```text
ext = "&role=admin&cmd=dump"
```

Set the engine's state to `sig`, feed `ext`, and read the new tag `sig2`. That `sig2` is a valid signature for the forged message:

```text
msg' = msg ‖ glue ‖ ext
```

because `secret ‖ msg' = secret ‖ msg ‖ glue ‖ ext` — exactly what the server will hash. When the server parses `msg'`, the trailing `&role=admin&cmd=dump` overrides the earlier `role=guest` (last-wins), so you are admin and the command is `dump`. The binary `glue` bytes in the middle just become junk tokens the parser skips.

### The one unknown: the secret's length

`glue` encodes the total length `L = len(secret) + len(msg)`, and you don't know `len(secret)`. So brute it. For each guess `s` in a small range you build a different `glue` and a different `sig2`; only the guess matching the real secret length verifies, and the device answers with the vault. Because the token (and its nonce) are per-connection and the secret is server-side and unknown, this can only be done **live** — which is the point.

Worked example (local instance, `secret = "d3adb0lt.dev.key"`, 16 bytes):

```text
msg = "salt=<32 hex>&uid=1000&role=guest"          → 57 bytes
L   = 16 + 57                                        = 73 bytes
glue= 0x80 ‖ 0x00×46 ‖ uint64_be(73*8=584)           = 55 bytes  (73+55 = 128, a block boundary)
msg'= msg ‖ glue ‖ "&role=admin&cmd=dump"
sig2= SHA256 state(sig) then absorb the extension
```

`solve.py` implements SHA-256 and the extension from scratch (no `hashpumpy`), so you can read every step.

## 4. Run it

### Full command walkthrough

```sh
# --- Stage 1: carve ---
binwalk -e deadbolt-flash.bin
cd _deadbolt-flash.bin.extracted/squashfs-root
find . -type f
cat etc/deadbolt.conf etc/banner etc/init.d/rcS
strings usr/bin/lockd | grep -iE 'sig=|role=|salt=|vault|urandom|DEVICE_KEY'

# --- Stage 2: run locally to study it ---
./usr/bin/lockd &            # "lockd listening on 6000"
LOCKD=$!

# --- Stage 3: exploit ---
python3 /path/to/solution/solve.py 127.0.0.1 6000     # local -> placeholder
kill $LOCKD
python3 /path/to/solution/solve.py <host> <port>      # live  -> real flag
```

Local output (secret length 16 = the dev key):

```text
[+] secret length = 16
[+] flag: DNCTF{local_dev_instance_not_the_real_flag}
```

Live output (secret length is randomized per container, so it varies):

```text
[+] secret length = 21
[+] flag: DNCTF{deadbolt_l3ngth_3xtension_ala_carte}
```

### Against the Docker container

```sh
cd src
docker compose up -d --build
python3 ../solution/solve.py 127.0.0.1 5002     # host 5002 -> container 6000
docker compose down
```

Verified end to end: carving reproduces `lockd` byte-for-byte, the solver reverses the framing, brute-forces the secret length, forges the signature, and retrieves the injected flag; a stock local instance returns only the placeholder.

## 5. What the vendor should have done

Use a real MAC. `HMAC-SHA256(secret, msg)` is not length-extendable, because the secret is folded in through the inner/outer padding rather than simply prefixed. Also: authorize on server-side session state, not on fields carried inside a client-supplied signed blob, and reject duplicate keys instead of letting the last one win.

## 6. Flag delivery in CTFd

`challenge.yml` uses `type: dynamic`, which is dynamic **scoring** (points decay with solves), not a per-team flag. The flag there is one shared static string and must equal the `FLAG` you inject in `src/compose.yaml`.

A genuinely different flag per team is **not** possible with a static flag list — CTFd compares every submission against the same string(s). For that you need a per-team container plugin (e.g. ctfd-whale) that spawns one `lockd` per team, injects that team's `FLAG`, and registers it. For a club event, the shared static flag is the sane choice; the handout contains no flag regardless, so the AI-paste concern is already handled. Do **not** use a regex flag like `DNCTF\{.*\}` to accept "any" flag — that lets teams submit `DNCTF{anything}`.

The entrypoint randomizes `DEVICE_KEY` (length 12–36) per container so the online length-brute stays part of the solve. Don't set `DEVICE_KEY` yourself.
