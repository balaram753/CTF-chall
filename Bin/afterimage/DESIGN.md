# Afterimage object model

This is the organizer prototype for the final challenge.

## Objects

`Snapshot` contains two shared raw pointers:

* `Image` holds a small snapshot header and data area.
* `Capability` holds a nonce, a privilege field, and audit bytes.

The two allocation types are intentionally the same size. They are not
interchangeable, but the allocator is unaware of their C++ types.

The intended ownership rule is that a snapshot reference keeps both objects
alive. The `revoke` path violates that rule: it deletes the checked-out
capability and clears only the current snapshot. Cloned snapshots retain the
old pointer.

## Intended exploit chain

1. `new base 7`
2. `clone branch base`
3. `checkout base`
4. `revoke`
5. `new filler 7`
6. `patch branch 8 2047987285`
7. `restore branch`

The new image is allocated immediately after the revoked capability and
reuses its allocator chunk. `branch` still treats that chunk as a
`Capability`. The only write primitive is a bounded four-byte write through
that stale pointer. Offset 8 is the privilege field according to the
capability layout, while it is the start of `Image::label` according to the
replacement object. Writing `0x7a11ce55` authorizes restore.

There is no pointer printer, arbitrary read, static flag, or `win` function.
The final player handout should contain only a stripped binary and connection
details. The dynamic flag is generated by the launcher and is not present in
the binary or filesystem.

## Fair difficulty

The difficulty comes from identifying the paired object model, reconstructing
the exact allocation order, noticing that two C++ types have an equal size,
and using the bounded write at the correct field offset. It should not use
prompt tricks, AI-targeted behavior, telemetry, or destructive input handling.
Those mechanisms do not prevent analysis of a supplied binary and would make
the service less fair and less reliable.
